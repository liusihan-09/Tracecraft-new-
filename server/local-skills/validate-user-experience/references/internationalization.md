## 1. 建立 locale profile

国际版评审前必须确认目标地区，不使用笼统的“英文版”代替本地化范围。

记录：

- 语言与语言变体；
- 国家/地区；
- LTR 或 RTL；
- 日期、时间、时区和首日规则；
- 地址顺序与邮编；
- 电话国家码和本地格式；
- 货币与数字分隔；
- 姓名顺序和字符集；
- 目标浏览器、设备和键盘；
- 文化、法律、支付、隐私或内容禁忌；
- 是否采用国际版移动云 UIUE 基线。

未指定 locale 时只能做通用国际化准备度检查，不能声称特定地区已通过。

## 2. 自然表达

检查：

- 翻译传达原意、语气和情感，不逐字直译。
- 专业术语、行业缩写和产品名称使用当地通行写法。
- 用户看到的是自然语言，不是内部字段、代码或后端报错。
- 同一对象、动作和状态在全产品中使用统一译法。
- 文案长度、复数、性别、数值插值和语序不会因拼接产生错误。
- 按钮和错误信息描述用户行动，不复制中文句式。
- 文案有上下文，翻译人员能够区分名词/动词、标题/按钮和对象。

不要把“没有中文残留”当作本地化完成。

## 3. 阅读方向与布局

常见阅读方向：

- LTR：中文、英文、韩文、日文等；
- RTL：阿拉伯语、波斯语、乌尔都语等。

RTL 核查：

- 文字和主要排版右对齐；
- 模块和导航顺序从右到左；
- 图文组合中 icon 与文字顺序符合 RTL；
- 方向性图标（箭头、前进/返回等）镜像；
- 非方向性图标不机械镜像；
- 时钟、电话号码和数字本身不镜像；
- 标签、分页、步骤条、表格固定列和抽屉方向适配；
- 键盘方向键、焦点顺序和动画方向与视觉一致；
- `dir`、语言属性和混合双向文本正确。

文本空间：

- 预留多语言膨胀，不固定依赖中文短文案。
- 段落优先左对齐；RTL 语言右对齐。
- 横向排布一行不多于 2 列的建议可用于国际版长文本场景。
- 优先纵向排列，为换行和错误信息留空间。
- 使用换行、滚动、省略+展开或省略+hover 时确保完整信息可访问。
- 不将单个英文单词错误拆行，如 `acc` / `urate`。
- 文本无截断、溢出、重叠、错位和控件挤压。

## 4. 地址、日期、电话、货币和数字

### 地址

- 中国地址通常从大到小；英美地址通常从小到大。
- 字段顺序、标签和必填规则按 locale 配置，不只翻译标签。
- 支持当地字符、州/省、邮编和无街道地址等差异。

### 日期与时间

规范示例：

- 北美常见 `MM/DD/YYYY`；
- 英联邦和欧洲多地常见 `DD/MM/YYYY`；
- 中国、日本、韩国、新加坡等常见 `YYYY/MM/DD`。

不要只显示模糊的 `03/04/2026`。必要时使用月份名称、locale 提示或标准格式消除歧义。

同时检查：12/24 小时制、时区、夏令时、周起始日、日期范围顺序和后端存储转换。

### 电话

- 根据国家地区显示本地格式。
- 提供国家码选择；国旗只能辅助，不作为唯一识别方式。
- 支持粘贴、空格、括号、连字符和国际号码标准化。
- 验证错误说明期望格式，不用单一正则拒绝合法号码。

### 货币

- 跨境、汇率或汇款场景优先 ISO 4217 代码，如 `USD 100.00`。
- 本地消费场景可使用当地常见符号或名称，但要避免同符号歧义。
- 明确含税/未税、计费周期、汇率时间和四舍五入。

### 数字

规范列出的主流示例：

- `1,234,567.89`：逗号千分位、点小数；
- `1 234 567,89`：空格千分位、逗号小数；
- `1.234.567,89`：点千分位、逗号小数。

输入、展示、导出、排序、搜索和接口返回要使用一致语义。不要把本地化显示字符串直接当数值比较。

## 5. 文化与包容性

检查图形、色彩、图片、插图、手势、动物、宗教、人物和节日是否存在当地歧义或禁忌。

规范提示：

- 不同文化对颜色含义不同；不能机械套用单一色彩情绪。
- 伊斯兰文化场景需谨慎使用狗、猪等元素。
- 某些文化对左右手、手势和身体部位有特定含义。
- 优先使用跨文化通用的基础图形和实物映射，避免为“创新”制造图标歧义。
- 人物图像避免单一肤色或刻板印象；必要时使用更包容或不强调真实肤色的视觉。

文化判断具有地区和语境差异。高风险结论需本地专家或用户验证，专家走查只能标记风险。

## 6. 英文大小写

规范定义：

- Sentence case：首字母和专有名词大写。
- Title Case：实词首字母大写，常见虚词小写。
- ALL CAPS：全部大写，谨慎使用。
- lowercase：全部小写，通常不作为默认 UI 文案样式。

场景规则：

- 主要页面标题/版块标题：Title Case。
- 主导航菜单：Title Case。
- 按钮文本：Title Case。
- 操作链接：Sentence case。
- 下拉菜单项：Sentence case。
- 输入标签：Sentence case。
- 占位符：Sentence case。
- 错误/成功消息：Sentence case。
- 表格列标题：Title Case。
- 列表项：Sentence case。
- 品牌/产品名：官方写法。
- 缩写：官方写法，常见首字母缩略词全部大写。

快速原则：默认 Sentence case；标题和导航使用 Title Case；尽量避免 ALL CAPS，除非标签或极端重要警告。

如果项目已有明确英文内容规范，以项目规范为准并记录差异。

## 7. 国际版视觉基线

来自国际版设计分册：

- 主品牌色 `#337DFF`。
- 字体优先顺序 San Francisco、Segoe UI、Roboto、Helvetica、Arial。
- 页面优先使用 San Francisco。
- Dashboard 数字字号常见 36/32/28/24/20/16/12px。
- 页面内容较少时正文推荐 12px；实际按组件层级和可读性判断。
- 正文行高通常为字号 1.5 倍。
- 数字与单位间加半角空格；度、百分比等符号类单位除外。
- 统一画板宽度 1366px。
- 有效内容区（含左导航）最小宽度 1200px；小于时出现横向滚动条。
- 产品统一使用 24 栅格系统。
- 水槽以 10n 为基础单位；具体比例按业务内容选择。
- 中后台左导航宽度 160px。

这些是国际版移动云基线，不应自动覆盖其他品牌或现代响应式项目。若用户要求按该规范验收，则视为硬性规则。

## 8. 国际版组件和典型页面

组件重点：

- 同一操作区主按钮最多一个。
- 选项少于 5 项时，优先考虑平铺 Radio，减少下拉认知成本。
- Switch 立即生效；Checkbox 通常配合提交。
- 默认分页 10 条，可按业务调整；翻页或改变每页条数不应丢失查询条件。
- 页数多时允许直接输入页码。
- 表格文字/图片左对齐，数字和金额右对齐。
- 不定长字段固定宽度并省略，hover/展开查看完整内容。
- 删除必须确认；删除后列表状态和页码合理更新。
- 提交/上传检查主标识重复和空值，防止重复提交，提供取消/返回和成功/失败反馈。
- 子页面提供返回路径。

典型页面覆盖：

- 控制台总览；
- 新手教学；
- 一/二级页面；
- 带或不带步骤条的表单；
- 无数据、未开通、开发中、暂无更多等缺省页；
- 订购、开通、手动/自动续订、规格变更、扩容、计费变更、退订、确认订单和结果页。

对于订退改续，重点验证价格、币种、税、区域、资源范围、不可逆影响、预计生效时间、结果状态和后续管理。

## 9. 输入输出与技术验证

国际化不只审文案。实现态至少验证：

- Unicode 输入、保存、读取和导出无乱码或丢失；
- 组合字符、emoji、非拉丁字符和长字符串；
- 本地化数字与日期的解析、排序和筛选；
- 服务端与客户端 locale 一致；
- 文案插值不会破坏语序；
- 复数和性别规则；
- RTL CSS logical properties；
- 截图、PDF、邮件和下载文件中的格式；
- 搜索是否支持本地字符、大小写和重音符号；
- 键盘、输入法和自动填充；
- 翻译缺失时的回退语言可理解，不显示 key；
- 时区转换和夏令时边界；
- 权限、法律、隐私和数据驻留文案与实际行为一致。

## 10. 报告要求

每个国际化问题记录：

- locale profile；
- 具体字符串、字段或页面；
- 目标规则和实际表现；
- 是否影响理解、输入、保存、排序、支付、法律或文化风险；
- 复现数据；
- 修复后的 locale-specific 验收标准；
- 是否需要本地专家或真实用户复核。

结论可以按 locale 分开，不用一个英语页面代表全球版本。
