## 1. 最小交付

即使用户只要求“看一下体验”，也至少输出：

1. 评审范围和模式；
2. 用户目标与核心任务；
3. 证据充分度和不可验证项；
4. 发布结论或暂不判定；
5. 按严重度排序的问题；
6. 每个问题的证据、用户影响、建议和验收标准；
7. 正向证据；
8. 复测清单。

## 3. 问题字段

### ID

使用 `EVA-001` 递增，在同一报告中唯一。复评保留原 ID；新问题使用新 ID。

### 标题

使用“条件 + 问题 + 结果”的短句，例如：

> 删除最后一条记录后仍停留在空页，用户误以为数据全部丢失

避免“交互问题”“体验不好”等空泛标题。

### 证据

至少一个可定位证据：

- `PRD 第 8 页 3.2.1`；
- `设计稿/创建实例/配置页/错误态`；
- `screenshot-04.png，右侧价格卡片`；
- `https://...，步骤 1-5，测试账号角色`；
- `src/pages/order.tsx:148`；
- `2026-08-03 10:22 日志/请求 ID`。

### 用户视角

用第一人称或接近用户思考的语言描述，例如：

> “我已经点击保存，但页面没有变化。我不知道是否需要再点一次。”

不要虚构情绪强度或行为数据。

### 根因

根因要落到可修复结构：状态模型、信息架构、反馈、组件选择、规则表达、数据同步或实现漂移。

### 建议

说明改变什么、放在哪里、何时出现、如何与现有模式一致。建议可以给方案选项，但要指出推荐方案和权衡。

## 4. 任务覆盖字段

每条任务建议包含：

- `id`：如 `TASK-01`；
- `name`：用户目标；
- `role`；
- `preconditions`；
- `criticality`：critical | important | supporting；
- `status`：success | partial | failed | not_tested；
- `states_tested`；
- `evidence`；
- `gaps`。

不要把“页面已打开”记为任务成功。成功必须对应业务结果。

```json
      "recommendation": "在总价旁展示价格变化原因和可展开费用明细。",
      "acceptance_criteria": [
        "金额变化时显示差额与原因",
        "费用明细与最终支付金额一致",
        "键盘和读屏可访问明细"
      ],
      "similar_checks": ["续订确认页", "变更计费页"],
      "confidence": "high"
    }
  ],
  "cross_cutting_risks": [],
  "gaps": ["运行环境不可用，未验证键盘和响应式"],

```

允许增加字段，不要改变校验脚本依赖的核心字段和枚举。

结论枚举：

- `pass`：通过；
- `conditional_pass`：有条件通过；
- `fail`：不通过；
- `undetermined`：暂不判定。

## 6. 验收标准写法

好的验收标准具备：对象、条件、动作、结果和可测量方式。

差：

> 优化错误提示。

好：

> 当实例名称已存在且输入框失焦时，在输入框下方显示“名称已存在，请更换名称”；焦点可移动到错误字段，用户修改为可用名称后错误消失，已填写的其他字段保持不变。

规范尺寸类验收标准要写测量环境，例如视口、缩放、设备像素比和组件状态。

## 7. 正向证据与缺口

正向证据不是礼貌性表扬。只记录对任务成功有价值且有证据的设计，例如：

- 高风险操作明确展示影响对象和不可逆后果；
- 提交失败后保留输入并定位错误；
- 跨页面数据与单位一致；
- 国际版正确处理 RTL 和本地日期；
- 加载只阻塞受影响区域。

缺口要说明它阻止了什么结论，例如：

> 只有默认态截图，无法验证键盘焦点、校验、加载和错误恢复，因此实现态暂不判定。

## 8. 标注图和复测

用户提供截图并要求视觉化报告时，可生成：

- 问题标注图：编号与报告 ID 一致；
- 优化建议图：只示意关键修复，不冒充最终视觉稿；
- 前后对比：标明“建议方案”与证据来源。

复评时：

- 保留原问题 ID；
- 标记 fixed | partial | not_fixed | cannot_verify；
- 引用新证据；
- 检查修复是否引入回归；
- 更新任务覆盖和发布结论，而不只更新问题列表。
